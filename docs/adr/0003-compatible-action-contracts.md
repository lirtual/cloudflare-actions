# ADR-0003: Compatible Action contracts instead of fixed Provider deployment pins

**Status:** Accepted design (2026-11-04); implementation and production cutover not performed.

Workflow MCP remains the sole general-purpose orchestrator. The independently released `cloudflare-actions` Worker provides the fixed, source-reviewed Action catalog through one private Service Binding; `github-actions` continues to own Runner Task/Session execution and `remote-control-agent` retains its separate native release lifecycle. Merging repositories or creating a new orchestration layer is not justified by the current maintenance cost.

**Decision:** For **new** Action dispatch, enforce the trusted Provider/service identity, Action ID, existing immutable Published Plan grant, Action contract digest, permitted arguments and side-effect scope. Treat a protected, source-reviewed deployment with behavioral compatibility tests as a compatible provider implementation regardless of its new Cloudflare Worker Version UUID. When authorization-relevant behavior, outputs, security boundaries or effects change, advance the **existing** Action contract version/digest and require fresh Plan approval even if the JSON Schema remains identical. Keep the fixed build-time registry and private binding: no dynamic plugin registry, new credential scope, compatibility service or alternate publisher. The observed runtime Provider Version remains execution evidence rather than a permanent compatible-dispatch pin.

**Immutable history and anti-replay:** Do not rewrite older Published Plans or their original grants. Existing D1 Run/Step/Invocation reservations retain their exact original deployment ID, contract/input digests, binding generation and outcomes. Missing/unknown receipts and already reserved invocations never permit a second external send. Before a **new** reservation, verify the live trusted Provider contract and capture the actual runtime deployment ID; the Provider validates the invocation against its current contract/identity. A pre-reservation mismatch denies admission, while an uncertain post-reservation result remains unknown with no automatic retry. Never silently authorize older retired Weixin Actions: historical aliases and Plans stay readable but execution remains denied at validation, admission and dispatch.

**Cutover and rollback:** Verify compatible Consumer behavior against the existing Provider **before** updating Provider; use the existing authorized GitHub Actions release mechanism, Cloudflare native versioning and D1 gates. Check in-flight and uncertain execution before changing an incompatible or sensitive path; freeze/drain only when the concrete transition requires it, not on every compatible update. An old Cloudflare version is **not** automatically an approved rollback. Any rollback or incompatible update needs an independently reviewed Bark-only target, checked contract and grant compatibility, explicit production authorization and post-release live readback; do not restore retired Weixin binaries/credentials.

**Scope:** A single four-repository Spec organizes separately verifiable work: (1) Provider/Consumer compatibility; (2) validated retirement of historical Weixin/cutover release code without deleting production data or anti-replay evidence; (3) unneeded CI/Workflow/Docs maintenance drift; (4) Agent fixture/protocol/release alignment. Preserve actual GitHub physical execution, immutable Agent releases, mandatory checks and independent production approval. This ADR revises only ADR-0001's exact-deployment-pin coupling for compatible **new** dispatch, not its one-Worker catalog, private binding or credential boundaries.
